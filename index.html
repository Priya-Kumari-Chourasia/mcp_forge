Every team writes this by hand

Exposing an API to an agent means reading its documentation, working out its auth scheme, writing tool functions, and testing that they actually work. A team with twenty internal APIs does this twenty times, by hand, and the documentation is rarely clean enough to make it quick.

MCP-Forge does this translation for you — and unlike asking an LLM once and hoping, it checks its own work at two separate points before handing you anything.

How it works

Four stages, each one a real agent decision — not a fixed script.

1

Orchestrator reads the docs first

Before anything else runs, an orchestrator agent classifies the API as simple or complex and routes execution down the right path.

2

Agentic RAG extraction

Structured endpoint info gets pulled from the docs, then graded for completeness. Missing a field? It re-queries automatically, with a refined prompt, instead of moving on with a gap.

3

Code generation

One MCP tool function gets written per endpoint, from the verified extraction — whether the API has one endpoint or thirty.

4

A2A-verified validation

The generated code is sent, over a real HTTP request, to a separate validator agent that statically checks syntax and structure — deliberately never calling the functions live, since every one of them is designed to hit a real external API. A failure comes back as a real error and triggers another generation attempt.

Plausible isn't the same as verified

A single prompt to an LLM can produce code that looks right. The problem shows up later, when someone tries to use it.

One prompt

Looks right

Generates once, returns whatever comes back. If a parameter name is wrong or an auth detail is missed, nothing catches it until someone tries to run the code.

MCP-Forge

Actually checked

The extraction grades its own completeness. The generated code is statically validated by a separate agent over A2A — syntax, structure, real callable functions. Failures are real errors, fed back automatically, until it passes or hits a retry limit.

What's in it

Real A2A communication

Code generation and testing run as separate, independently started services, exchanging task/message/artifact JSON over HTTP — not a function call pretending to be a protocol.

Self-correcting extraction

The documentation-reading step doesn't trust its first answer. It grades itself against required fields and retries with a sharper prompt when something's missing.

Multi-endpoint aware

Handles a one-endpoint API and a thirty-endpoint API through the same pipeline, generating one function per endpoint either way. Verified against a live 19-endpoint public API.

Deterministic OpenAPI parsing

A structured OpenAPI or Swagger spec is parsed directly — no LLM call, no risk of misreading something that was already machine-readable.

Point it at your own docs

A real command-line interface — a file, a URL, or raw text. No code editing required to run it against a different API.

Swappable LLM backend

Ships with a free offline stub for fast iteration, and a real Groq integration for production use — one environment variable apart.

Free to run, start to finish

Groq's free tier for inference, Oracle's Always Free tier for hosting. No card required for either.

Get started

Runs free and offline out of the box. Add a Groq key when you want real generation.

# install pip install -r requirements.txt # run free, offline — no key needed python graph.py --text "GET /ping - health check" # point it at your own API's live OpenAPI spec python graph.py --url https://your-api.com/openapi.json # or a local file of prose documentation python graph.py --file my_api_docs.txt
